# Бібліотека інструкцій ERP · 0.27.0

**Розгорнуто 2026-09-08**, runtime `42a1dff40eb6352abc542309d1ab9299d0432604`. Відкрити [бібліотеку LABA](https://laba.zpseapil.club/erp#guides). Адміністратор керує інструкціями тут, не в загальній `/admin`. Підтверджений стан і резервні копії — `CURRENT_STATE.md`; початково бібліотека порожня, інструкції додає власник за реальними процедурами.

Кнопка **«Інструкції»** у навігації ERP відкриває «Корисні матеріали»: пошук, картки процедур, покрокове читання з фотографіями. На телефоні це той самий захищений сайт, без встановлення окремого застосунку. Темна та світла теми успадковані від LABA. Це бібліотека, а не зміна обліку робіт, норм матеріалів чи складських проводок.

## Для майстра

1. Відкрити «Виробництво ERP» → «Інструкції».
2. Знайти матеріал за назвою, категорією, моделлю або текстом кроків; пошук українською нечутливий до регістру.
3. Натиснути «Читати». Зміст переходить до потрібного кроку; фото можна відкрити окремо для збільшення.

Майстер бачить тільки опубліковані, неархівні інструкції. Доступ мають усі активні ERP-ролі; створення, фото, чернетки, редагування та архів — тільки ERP `admin` (включно з глобальним адміністратором). ERP `manager` не є адміністратором бібліотеки. Видалення користувача з allowlist/ERP відкликає доступ при наступному запиті. Уже побачене чи самостійно збережене фото відкликати з телефона неможливо.

## Для адміністратора

1. «Нова інструкція»: назва (до160 символів), необов'язкові категорія80, модель120, опис500.
2. Додати 1–30 кроків: назва120, пояснення6000, за потреби фото та підпис300. Кроки можна переставляти.
3. **Спочатку зберегти чернетку.** Лише після цього доступне завантаження фотографій. Нових інструкцій максимум1000 включно з архівом.
4. Завантажити фото у відповідний крок. Фото одразу захищено збережене, але його прив'язка до кроку потребує «Зберегти чернетку» або «Опублікувати». «Раніше додані фото» дозволяє повторно використати завантаження цієї інструкції, зокрема після закриття незбереженого редактора.
5. Перевірити «Попередній перегляд» і натиснути «Опублікувати». Кожен крок повинен мати назву та текст або фото. Незавершена чернетка не з'являється у майстрів.
6. Подальші правки зберігаються окремо від опублікованого знімка. Майстри бачать попередню публікацію, доки адміністратор явно не опублікує нову.
7. «До архіву» приховує матеріал та його фото від читачів без видалення. «Повернути з архіву» повертає попередню опубліковану версію; чернетка без публікації залишається приватною.

Закриття/перезавантаження із незбереженим текстом запитує підтвердження. HTTP409 не знищує форму: інший адміністратор змінив версію; скопіюйте свій текст і відкрийте актуальну інструкцію. Автоматичного merge тексту немає. Звичайний текст не виконується як HTML/Markdown, сторонні iframe/скрипти/посилання на довільні фото не вставляються.

## Фото та межі захисту

- JPG/JPEG, PNG, WebP: до6MiB, до16мільйонів пікселів, статичне зображення. SVG/GIF/PDF/відео/анімації не підтримуються. HEIC з iPhone потрібно експортувати як JPEG.
- Сервер перевіряє розширення, сигнатуру та фактичний decode; MIME браузера не є доказом формату. Sharp0.35.4 перекодовує до WebP, автоматично повертає за EXIF, прибирає метадані, обмежує довгу сторону2000px. Результат не більше2MiB. Оригінальний файл та його ім'я не зберігаються.
- Один decode одночасно, concurrency1, cache вимкнено, input limits та processing timeout5сек. Повторний паралельний upload може повернути429; повторіть через кілька секунд. Це не окремий sandbox або антивірус: бібліотеки decode треба оновлювати після security advisory.
- Окремий upload rate limit12/хв на адміністратора; тільки цей endpoint допускає JSON base64 body до8MiB+1024. Інші ERP write endpoint залишаються256KiB. Cloudflare JWT, локальний allowlist, ERPadmin, exact Origin, Fetch Metadata, X-Portal-Request та UUID обов'язкові.
- До100 збережених фото на інструкцію та сумарно256MiB оптимізованих фотографій. Архівні/від'єднані фото теж враховуються. Автоматичного видалення немає; UI показує заповнення сховища. Для розширення потрібні оцінка диска/backup та узгоджена зміна квоти.
- Фото видаються тільки `/api/erp/guides/:id/images/:uuid` після перевірки прав і належності. Неадміністратор може отримати тільки фото, на яке посилається актуальна публікація. `image/webp`, nosniff, no-store, same-origin CORP. Немає публічного каталогу, зовнішнього storage/CDN чи передавання фото на сторонній сервіс перевірки.

Рішення спирається на [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), [Sharp input limits](https://sharp.pixelplumbing.com/api-constructor/) та [Sharp output/metadata/timeout](https://sharp.pixelplumbing.com/api-output/). Це defense-in-depth, а не гарантія від усіх кібератак чи незалежний penetration test.

## Дані, сумісність та продовження з іншого ПК

Міграція `erp_guides_v1` тільки додає `erp_guides`, `erp_guide_images` та індекс. Старі таблиці/кількості/таймери/ролі не переписуються. `draft_json` та `published_json` — незалежні знімки; `version` потрібна для optimistic concurrency. Запис документа, audit та UUID replay атомарний у наявній IMMEDIATE-транзакції. Фото перевіряється до транзакції, а версія/квота повторно перевіряються вже у транзакції. Аудит зберігає текстові зміни/метадані фото, але не дублює BLOB/base64.

Фото лежать **BLOB у тій самій SQLite**, не у Git. Штатний SQLite `.backup` включає і тексти, і зображення атомарно. Це спрощує відновлення, але збільшує БД, WAL, час та розмір усіх backups. Перед підвищенням квоти перевірити вільний диск, retention, час відновлення й MemoryMax512MiB. Не копіювати лише DB-файл працюючого WAL-сервера звичайним cp. Offsite backup досі не налаштований: копії на тому самому VPS не захищають від його втрати.

Пріоритет rollback — fix-forward. Не замінювати живу БД старою копією поверх нових записів. Якщо тимчасово повертається код0.26.2, зберегти нові таблиці/зображення і всю актуальну БД; бібліотека просто буде недоступна у старому UI. Старіші семантичні обмеження ERP_TEAMS/ERP_MATERIALS залишаються чинними. Секрети, фото, робочі інструкції та бази до Git не додавати. Git містить тільки код/документацію та синтетичні тести; реальні процедури додає уповноважений адміністратор майстерні.

Основні файли: `src/erp-guides.mjs`, `src/erp-guide-images.mjs`, `src/erp-routes.mjs`, `public/erp-guides.js`, `public/erp-guides.css`. Підключення через `public/erp.js` і `public/erp.html`; статичні version tags0.27.0. `sharp` exact version у package/lock, `.npmrc ignore-scripts=true` збережено; Linux optional native packages треба перевірити у staging, а не копіювати Windows node_modules.

## Перевірки

```bash
npm ci
npm run check
npm test
npm audit --omit=dev
node scripts/erp-guides-browser-check.mjs
node scripts/erp-notifications-browser-check.mjs
node scripts/erp-scrollbars-browser-check.mjs
node scripts/erp-migration-check.mjs /absolute/path/to/source.db
```

Browser check потребує Playwright та Chrome, підтримує `PLAYWRIGHT_MODULE`/`PLAYWRIGHT_CHANNEL`. Він запускає власний localhost8088, створює синтетичну БД і просте тестове зображення, перевіряє admin/worker, draft/publish/conflict, upload/reuse, archive/restore, пошук/зміст, desktop1440 dark/light, mobile390 dark/360 light та mobile editor. Тимчасова БД видаляється; скриншоти тільки ignored `data/`. Не запускати UI-сценарії з тестовими POST на production. Migration checker відкриває джерело read-only та двічі мігрує disposable SQLite backup, звіряючи старі таблиці/значення/markers.

Підтверджений production runtime SHA, backup, результати staging та фактичний стан release — **тільки `CURRENT_STATE.md`**, не номер package.json і не припущення за Git HEAD.
