# Двостороння синхронізація Сервісу

Працює через наявний приватний accounting API та SignalSynch. Нові Google credentials, публічні маршрути або Signal-повідомлення не потрібні. Коментарі з `Обліку` не редагуються вручну в LABA; виняток: автоматичне доповнення колонки коментаря датою відправлення/повернення. Робочі примітки, рапорт, мітки та статуси роботи зберігаються в LABA.

## Відправлення та повернення (16.09.2026)

- Ручний перехід у `Відправлено` додає `Відправлено на сервіс: DD.MM.YYYY, HH:mm:ss` (для тари: `Тару відправлено: ...`). Час фіксується в `Europe/Kyiv` у момент переходу, а не доставки в Google.
- Нова системна колонка `returned` / `Отримано після сервісу` записує `ПОТРЕБУЄ ОГЛЯДУ`, розташування борта й тари `ЛАБА`, коментар `Повернувся із сервісу: ...`. Статус, обидва розташування і доповнений коментар відправляються одним RAW batch update.
- `ТАРА` зі статусом `ВТРАЧЕНИЙ` не може перейти в `returned`: API повертає 400 без outbox або зміни картки.
- Повернена сервісна картка лишається в `returned` з історією та рапортом; `ПОТРЕБУЄ ОГЛЯДУ` також створює/відновлює картку Майстерні за налаштованими вхідними статусами. Повторний статус сервісу починає новий цикл у тій самій картці. Зміна статусу на огляд і розташування на ЛАБА безпосередньо в таблиці також повертає відомий відправлений борт без echo-запису.
- `accounting_outbox.comment_append` зберігає незмінний текст події, `maintenance_cards.service_returned_at` утримує завершену історію. Повторне сортування в межах колонки, snapshot, ack, збереження налаштувань і перезапуск не генерують нові коментарі. Старі відправлення не отримують вигаданих дат.
- SignalSynch перечитує поточний аркуш, перевіряє точний ідентифікатор рядка і статус, зберігає попередній коментар та додає рядок лише за його відсутності. Якщо колонки коментаря немає або вона переповнена, жодна частина batch не записується, дія залишається з помилкою для повтору.
- Міграція додає колонку один раз у кінець дошки, не змінює адміністраторські назви, порядок, кольори чи доступи. Спочатку розгортати сумісний SignalSynch, потім LABA.

## Облік → Сервіс

- Вхідні статуси, як і раніше, визначає адміністратор дошки. Розташування саме по собі не створює сервісну картку для довільного справного борта.
- Звичайний сервісний борт: розташування **борта** `КИЇВ` або `НА РЕМОНТІ` означає колонку із системним ключем `shipped` (`Відправлено`). Розташування лише тари не підтверджує відправлення борта.
- `ВТРАЧЕНИЙ`: картка `ТАРА` вважається відправленою тільки за розташуванням **тари** `КИЇВ`. Розташування втраченого борта не використовується.
- Відправлені картки залишаються на дошці. Це замінює попереднє правило приховування тари в Києві/підтверджених сервісних відправлень. Наявні архівні рядки відновлюються з тим самим ID та історією, якщо вони знову надійшли з відповідним вхідним статусом.
- Якщо підтверджене розташування змінено на інше, картка з `Відправлено` повертається у налаштовану вхідну колонку. Якщо вхідний статус більше не належить дошці, картка прибирається з її активного списку; дані не видаляються.
- Незмінений snapshot не скидає вручну обрану проміжну колонку. Відсутні поля розташування не означають очищення, а порожні/часткові snapshots не прибирають рядки, яких у них немає.

## Сервіс → Облік

- Ручний перехід невідправленої `ТАРИ` у `Відправлено`: записати `КИЇВ` тільки в розташування тари.
- Ручний перехід невідправленого сервісного борта у `Відправлено`: записати `НА РЕМОНТІ` в розташування борта та тари. Статус рядка не змінюється.
- Після успішного ack сервісна картка залишається у `Відправлено`. Повторний snapshot або збереження налаштувань дошки не створюють повторну outbox-дію.
- Проміжні колонки не мають автоматичного зворотного запису розташування. Фізичне повернення звичайного борта оформлюється через `Отримано після сервісу`.
- Майстерня зберігає попередню поведінку: кінцева колонка записує налаштований статус, успішний ack прибирає картку з активної дошки.

## Конфлікти та перевірки

Нові nullable поля `maintenance_cards.source_board_location` і `source_case_location` зберігають останній стан джерела між перезапусками. Міграція лише додає поля, не переписує старі значення. Вхідне переміщення записується в історію з автором `Облік`.

Вже досягнуті цілі outbox підтверджуються без повторного запису. Застаріла pending-дія скасовується при зміні статусу, номера борта чи відомого розташування в отриманому рядку. Пізній ack скасованої дії не змінює картку. Це не розподілена транзакція з Google Sheets: SignalSynch перевіряє рядок і пише через наявний API; одночасна зовнішня правка під час самого мережевого запису залишається обмеженням інтеграції.

Перевірки: `npm run check`, `npm test`, `npm audit --omit=dev`. `test/maintenance-sync.test.mjs` покриває обидва напрямки, ідемпотентність, конфлікти, зміну модуля, часткові snapshots, збереження метаданих, restart та міграцію попередньої схеми. `scripts/maintenance-sync-browser-check.mjs` перевіряє polling без reload, історію та desktop/mobile на disposable localhost. Для зовнішнього Playwright можна передати `PLAYWRIGHT_MODULE` та `PLAYWRIGHT_CHANNEL` за шаблоном інших browser-check скриптів. Production-тестові записи та повідомлення заборонені.
